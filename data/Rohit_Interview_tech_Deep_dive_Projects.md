## Quick-fire cheat sheet (read this first if you're short on time)

1. **"Why CDC instead of federated Trino queries?"** — Federation re-scans/re-joins Mongo on every query with no incremental state; CDC (Debezium→RisingWave→StarRocks) computes joins once, incrementally, and serves pre-computed results. Cost: eventual consistency, at-least-once delivery, MV-rebuild gaps.
2. **"Why not the Iceberg lakehouse POC you evaluated?"** — You hit real 429 "metadata too large" errors under continuous small CDC writes. Root cause was more specific than "Iceberg can't do small writes": BigLake's catalog-impl client didn't support the `CALL` maintenance procedures needed to compact behind them — switching to the native REST catalog client against the same endpoint fixed it (measured: files -81%, manifests -94%), so it's a catalog-tooling gap you found and fixed, not a hard Iceberg wall. What's still real: that's an extra piece of production infra (a scheduled maintenance job) a continuous-ingestion workload needs and RisingWave doesn't. Upserts on Iceberg via PyIceberg were also a manual delete-then-append (non-atomic, two commits) since MERGE INTO wasn't available outside Spark. StarRocks gives upsert + serving-latency natively; RisingWave gives correct incremental streaming natively — you were hand-building both on top of Iceberg.
3. **"Why a custom Trino connector instead of Trino's built-in MongoDB connector?"** — Dynamic per-tenant schema from an external schema service, org/account-scoped multi-tenancy baked into the catalog schema name, and OPA policy pushed down as query filters — none of that exists in a generic connector.
4. **Security finding to own, unprompted if it comes up:** `MongoClientFactory`'s TLS TrustManager has an empty `checkServerTrusted` (accepts any server cert). Real answer: client-side X.509 mutual auth is legit; server-trust relies on VPC-only reachability, which is a real but incomplete argument — the fix (pin the CA/cert) is small and you'd do it first if given a day.
5. **Architecture hack to own, unprompted if it comes up:** predicate pushdown for LIKE/JSON-path filters uses reflection into Trino's internal `Constraint`/`LayoutConstraintEvaluator` classes. Defensible because every reflective call is wrapped in try/catch that falls back to correct-but-slower Trino-side filtering — a Trino version bump can only cost performance, never correctness.
6. **Blue-green StarRocks swaps** — why: a schema/logic change to a live-read table can't be applied in place. How readiness is determined: not `information_schema.loads` (empirically wrong/stuck), but polling `rw_catalog.rw_streaming_jobs.status = 'CREATED'` plus a StarRocks-side settle window and row-count/existence check.
7. **Freshness/SLA numbers (30s report-load, sub-60s freshness)** — you have hard evidence for ~5–7s sink lag on the changelog path (local stack, documented). Be honest that production-at-scale validation of the full sub-60s claim across all MVs is a gap you'd want live Grafana dashboards to restate cold.
8. **Cost optimization (~20%)** — concrete levers: RisingWave Hummock checkpoint cadence + GCS bucket region co-location (cross-region egress), batched/rate-limited SQLMesh deploys (`run_plan_batched.sh`), cheap `LIMIT 10` existence checks instead of `COUNT(*)`. Be honest you don't have the exact cost-attribution breakdown per lever.
9. **Multi-tenancy via string-parsed schema names (`cortex_{org}_{account}`)** — fragile because account IDs can contain underscores; there's a real patch for it ("join all parts after org") that works but is one format assumption from a data-isolation bug. Cleaner design: structured identifiers instead of parsing a namespace out of a string.
10. **What "stopped scaling with study volume" means concretely** — N+1 synchronous schema-service calls per org during split planning, shared-cluster load contention with live OLTP traffic, and CPU/memory-bound row transformation inside the connector process itself.

# Part 1 — MongoDB → Debezium → RisingWave → StarRocks (production CDC platform)

## 1. Why CDC instead of federated Trino over Mongo?

**Q1: You could have just pointed Trino's MongoDB connector at the replica set and skipped this whole pipeline. Walk me through why you didn't.**

Federated query against Mongo works until you actually load it — every dashboard query becomes a live scatter-gather against the oplog-serving replica set, competing with OLTP traffic for the same secondary reads, and Mongo's connector for Trino pushes down almost nothing beyond simple predicates, so joins across collections happen in Trino's memory. At our scale — dozens of studies, tens of entity materialized views joining `c_event` × `c_task` × `c_public_user` × `c_site` for things like `subject_events_mv` — that's a full collection scan fanned out per query, every time, with no incremental state. CDC flips the cost model: Debezium reads the oplog once, RisingWave incrementally maintains the joins and aggregates as materialized views, and StarRocks serves the pre-computed result with real indexing and columnar scans. The query gets cheap and repeatable instead of expensive and repeated.

What it costs: eventual consistency (RisingWave→StarRocks sink lag), schema drift risk between Mongo's schemaless documents and StarRocks' typed columns, and delivery semantics that are at-least-once, not exactly-once — the design doc says explicitly that consumers must dedupe on `(pk, changelog_ts, op)`. We also inherited MV-rebuild semantics as a real operational concern — when SQLMesh restates a model, the downstream changelog MV rebuilds and re-emits every row as a fresh Insert, and rows deleted *before* the rebuild never get a Delete event replayed. That's a documented, accepted gap ("the unavoidable gap"), not something federation would have had to deal with at all.

*Be ready to defend:* the reconciliation safety net for that MV-rebuild gap — a snapshot-PK endpoint for clients to anti-join against — is still "Implementation TBD" in the design doc. If asked what happens today when a client's mirror has a ghost row from a rebuild: nothing automatic yet.

## 2. The BSON normalization SMT

**Q2: Why do you need a custom Debezium SMT at all instead of consuming Mongo's Debezium output directly?**

Debezium's MongoDB connector emits BSON in canonical extended-JSON — `$oid`, `$date`, `$numberDecimal`, `$numberInt`/`$numberLong`, `$binary` (legacy v1 two-field shape and v2 single-object shape), `$regularExpression`, `$timestamp`, `$minKey`/`$maxKey`. That's correct BSON round-tripping, but not something a SQL engine's JSON parser can consume as typed columns without special-casing every wrapper shape at every downstream layer. Rather than push that logic into every RisingWave source definition, we centralize it once in `BsonNormalizerTransform.java`, a Kafka Connect SMT that recursively walks the record and normalizes every extended-JSON form into plain JSON before it reaches Pub/Sub. It also promotes `_id`/`object` to top-level fields via `coalesce(after, before)` and drops the raw `before` field, so RisingWave's CDC source parsing has one consistent shape regardless of op type.

**Q3: Deletes carry no `after` in Debezium's envelope — how does the SMT get a primary key in that case, and what about v1 vs v2 `$binary`?**

On a delete, `after` is null and `before` is dropped from the normalized payload, so the SMT falls back to extracting `_id` from the Debezium record *key* — via `extractIdFromKey(record)`, reading the raw, un-normalized Kafka record key (something like `{"id": "{\"$oid\": \"...\"}"}`), not the value the SMT itself produces. That always carries the document's `_id` regardless of op type — but it's a real coupling point that would silently break if the key schema ever changed without updating the SMT. On `$binary`: v1 is `{"$binary": "<base64>", "$type": "<hex>"}`, v2 collapses that into `{"$binary": {"base64": "...", "subType": "..."}}` — Debezium can emit either depending on version/config (our own seed data has both shapes side by side across real documents), so the normalizer recursively detects and handles both. Same idea for `NaN`/`Infinity`: BSON floats can carry those, standard JSON has no literal for them, so they're sanitized before serialization or the JSON encoder downstream throws / RisingWave's parser rejects the row outright.

One structural detail worth knowing cold: the SMT is registered as `BsonNormalizerTransform$Value` in `application.properties`, not `$Key` — Kafka Connect SMTs follow a `Transformation<R>` interface with a `Value`/`Key` inner-class pattern so the same transform logic can target either channel, and we deliberately only touch the record *value*. The key is left completely untouched, still in raw Debezium form — which is exactly why the delete-path fallback above has to read the raw key rather than anything the SMT normalized.

**Q4: What happens if the SMT hits a BSON type it doesn't recognize, or is misconfigured?**

This is the design decision I'd defend hardest: the SMT **fails open** — but it's worth being precise about the two distinct layers that means, because they're not the same mechanism. Layer 1: an unrecognized `$`-type sentinel inside `convertBson()` doesn't throw at all — it's a silent per-field passthrough, `return bson` unchanged, no exception, no log line. That's deliberate: one unfamiliar wrapper shape inside one field of a large document shouldn't blow up the whole record. Layer 2: the outer `apply()` method wraps the whole normalization pass in a try/catch for genuine failures — malformed JSON that won't even parse — and *that* layer logs to stderr and passes the entire original, un-normalized record through unchanged rather than dropping it. So "fails open" is really "silently open at the field level, loudly-but-still-open at the record level." The alternative — drop the record — is strictly worse for a CDC pipeline: a silently dropped insert or delete is a permanent, invisible correctness gap in every downstream materialized view, and by the time anyone notices, there's no way to know whether it was dropped by the SMT, lost in Pub/Sub, or filtered somewhere else. Fail-open converts a hard correctness bug into an operational one — visible (at least at the parse-failure layer), alertable, debuggable — instead of a silent hole.

*Be ready to defend:* fail-open is a real tradeoff, not a free lunch, and the honest gap is worse at Layer 1 than Layer 2 — a genuine JSON parse failure at least logs to stderr, but an unrecognized `$`-type sentinel passing through a single field produces *zero* log output by design. If an unhandled BSON shape hits enough documents, RisingWave's CDC source table can start rejecting or misparsing rows at scale with no signal at all from the layer that actually let it through. Have a real answer for "how do you *know* this is happening in production" (dead-letter metrics, log-based alerting on Layer 2, plus something you don't currently have for Layer 1) rather than assume it won't be asked.

## 3. RisingWave's role specifically

**Q5: What happens in RisingWave versus StarRocks? Why split the work across two systems?**

RisingWave owns everything genuinely streaming and incremental: parsing the normalized CDC envelope into typed columns, and maintaining ~65 entity materialized views — including multi-way streaming joins like `subject_events_mv` — incrementally as CDC events arrive, so the join result is always current without re-scanning source tables. It also owns the changelog primitive: `WITH src AS CHANGELOG FROM <name>_mv` turns an upsert-semantics MV into an explicit stream of Insert/Delete/UpdateInsert/UpdateDelete rows — not something StarRocks can do; StarRocks only ever sees the row shapes RisingWave hands it. StarRocks does none of the transformation — it's the serving layer, taking RisingWave's sink output (upsert into PRIMARY KEY tables for current state, or append-only DUPLICATE KEY tables for changelog history) and serving it with real indexing, partitioning, and MPP execution. Each system does the half it's good at.

**Q6: Why RisingWave over Flink or ksqlDB?**

The concrete deciding factor: we explicitly evaluated and rejected RisingWave's native `CREATE SUBSCRIPTION`/`DECLARE CURSOR` mechanism (cursor sessions die with the DB connection, no buffer against MV rebuilds, doesn't scale to many external clients) in favor of `AS CHANGELOG` feeding a durable StarRocks sink instead.

More broadly, it's worth having the comparison on more than one axis, because "RisingWave is simpler" undersells it and "Flink is more mature" undersells RisingWave:

*Programming model.* RisingWave is SQL-native, full stop — you write `CREATE MATERIALIZED VIEW` and it's continuously, incrementally maintained; the ~65 entity MVs and multi-way streaming joins (`subject_events_mv` joining `c_event` × `c_task` × `c_public_user` × `c_site`) are all just SQL. Flink's primary model is a DataStream/Table API job graph — Flink SQL exists and has improved a lot, but the operational unit is still a compiled job, not a live queryable view. ksqlDB is SQL too, but its dialect and join/windowing surface is narrower — built around Kafka Streams' topology model underneath, which shapes what kinds of joins and state it handles well.

*Queryability.* This is the one that actually mattered for us: a RisingWave MV is a live, directly queryable Postgres-wire-protocol relation — `psql`, our tooling, SQLMesh's connection layer, and later `AS CHANGELOG` all just work against it as a normal database object. Flink's output generally isn't queryable until it lands in an external sink (its own state is opaque to outside readers without something like Flink SQL's changelog stream or a queryable-state API that's had a rockier maturity story); ksqlDB does support pull queries against materialized state, closer to RisingWave's model, but within its narrower SQL/join surface.

*Operational model.* RisingWave here is a single database-shaped system (Postgres wire protocol in, Hummock — its own state store — checkpointing to GCS in the background) — one thing to operate, one connection story. Flink means a cluster: JobManager/TaskManager topology, a state backend, checkpoint/savepoint lifecycle to manage for every deploy — real operational depth, and real operational cost, for a data-platform team that doesn't want to also become a Flink SRE team. ksqlDB rides on a Kafka Streams runtime — lighter than a Flink cluster, but still its own operational surface, and still bounded by Kafka Streams' semantics.

*Honest cost we did pay:* RisingWave can't `ALTER` a live materialized view's query in place — any change to an MV's SQL means drop-and-recreate, which is a full backfill from source, not an incremental migration. That's a real gap versus Flink's more mature savepoint-based state-migration tooling for evolving a running job. We accept it because our MV definitions are relatively stable day to day and the blue-green StarRocks flip already exists to hide a backfill window from readers — but if the team were doing frequent, large-state schema evolutions, that's a point where Flink's tooling is genuinely more capable, and I'd say so directly if asked "doesn't Flink handle this better."

For a data-platform team our size, "materialized views over Postgres wire protocol, one system to operate" won on operational surface and query ergonomics — at the honest cost of a less mature story for evolving live state in place.

## 4. Blue-green table swaps on StarRocks

**Q7: Why blue-green rather than in-place upsert for the StarRocks serving tables?**

Because a schema or logic change to a materialized view can't be applied safely to a table actively being read by dashboards and the changelog API mid-change. `sr_blue_green.py` (a custom `CustomMaterialization`) implements create-new/promote/drop-old: `create()` emits `CREATE TABLE contexts.<name>__<hash>` with StarRocks-specific DDL (PRIMARY KEY tables for current-state upsert semantics, DUPLICATE KEY for append-only changelog history), `insert()`/`append()` are deliberate no-ops because the data is owned externally by the RisingWave sink, and `promote()` is *also* a no-op — the actual view flip is deferred to `flip_sr_views.py`, which only runs after the RisingWave sink for that table is confirmed live and delivering data. Flipping the stable view before the sink is backfilled would expose an empty/partial table to every reader instantly. Blue-green means readers only ever see one fully-populated table or the other, atomically, via `CREATE OR REPLACE VIEW`.

**Q8: How do you determine a new table is "ready" to flip to, and what could go wrong during the flip?**

First cut was waiting for `information_schema.loads` to show `STATE='FINISHED'`. Empirically wrong — for RisingWave's Transaction Load (2PC) protocol that view was observed stuck at `BEFORE_LOAD` for a confirmed-zero-row table and `PREPARED` for confirmed multi-hundred-row tables, and its history is garbage-collected. What we settled on instead is job-dependent, not time-dependent: poll `rw_catalog.rw_streaming_jobs.status = 'CREATED'`, which transitions synchronously with `CREATE SINK` and always eventually resolves. Then, because `CREATED` only proves RisingWave's side finished (not that StarRocks can serve a read — we saw this fail live against a compute-node crash/restart), `flip_sr_views.py` layers a StarRocks-side check: a settle window, a row-count check, a patience window, then falling back to a cheap `LIMIT 10` probe against the upstream RisingWave relation (deliberately not `COUNT(*)`, which can be an expensive batch scan under load). One real wrinkle we hit as a false positive: changelog-stream tables filter to a 15-day recency window on top of the raw upstream MV, so "the raw upstream has rows" doesn't imply "the changelog stream has anything to emit right now" — three genuinely healthy streams got held back because their upstream only had rows older than 15 days.

On what can go wrong: partial visibility isn't a risk during the flip itself — `CREATE OR REPLACE VIEW` is a single atomic DDL statement, so a concurrent reader gets either the fully-old or fully-new table, never a torn mix. The real risk window is around it: sink retirement (dropping the superseded sink after a flip) is explicitly best-effort — logged on failure, not fatal — so an orphaned sink can in principle keep writing to a table nobody reads anymore.

*Be ready to defend:* `_current_physical()` discovers which physical table a stable view currently points at by regex-parsing `SHOW CREATE VIEW` output. Works, but brittle to any change in how StarRocks formats that output — own it as a known fragility if pressed.

## 5. SQLMesh as the modeling/deployment layer

**Q9: What's SQLMesh doing here that a plain deploy script couldn't, and why SQLMesh over dbt?**

SQLMesh gives a real plan/apply model with environment promotion and snapshot-based state (diffing, TTL-based GC, safe restatement that triggers a blue-green rotation for a single model), and a pluggable `CustomMaterialization` API that let us teach it a StarRocks-specific lifecycle without forking the tool. `run_plan.sh` orchestrates two SQLMesh gateways against the same project — `starrocks` (physical tables, blue-green) and `risingwave` (the materialized views) — in a specific order: phase 1 creates/updates StarRocks physical tables, then resolves the newest physical table per base name into a mapping, phase 2 deploys the RisingWave MVs and upsert sinks (which need that mapping to know where to write), then changelog sinks are created out-of-band via `psql` directly (RisingWave's `AS CHANGELOG` syntax isn't supported by SQLMesh's SQL dialect layer), and finally the stable views get flipped. Production runs batched with a sleep between batches specifically to reduce cluster load during a full redeploy.

Why over dbt: dbt's materialization model doesn't give a first-class hook for something like blue-green StarRocks table lifecycle without heavy custom-materialization macro work, and dbt has no native concept of a streaming-SQL gateway alongside a warehouse gateway in one project the way SQLMesh's multi-gateway config does — a `risingwave` gateway and a `starrocks` gateway side by side, with the StarRocks one riding a custom engine adapter (`SUPPORTS_TRANSACTIONS=False` because StarRocks rejects DDL inside explicit transactions).

*Be ready to defend:* the StarRocks gateway's SQLMesh state backend falls back to a local DuckDB file when `STATE_DB_HOST` isn't set — fine for local/CI, a real footgun if a production deploy ever runs without it wired to the shared Postgres state DB.

## 6. The Changelog Streaming API (FastAPI)

**Q10: Walk me through the cursor design — why ingestion time instead of event time, and how do deletes/late data survive pagination?**

The first cursor design used event time — `(changelog_ts, pk)`. Broken for two cases: a delete carries the *same* timestamp as the row's prior insert (deleting doesn't touch `updated`/`created`), so the two-way comparison can collapse the delete's position with the insert's and skip it; and once a client's high-water mark passes some event time, any row landing later but timestamped earlier (late write, replayed CDC, clock skew) falls behind the cursor and is silently never delivered. We moved the cursor axis to `(synced_at, _changelog_row_id)` — `synced_at` is filled by StarRocks at insert time, monotonic in *visibility* order by construction, and `_changelog_row_id` is RisingWave's internal per-emit monotonic sequence as the tiebreaker. Since it's ingestion time, late data always sorts after the cursor rather than getting skipped — the cost is at-least-once delivery, which is why the API contract requires clients to dedupe on `(pk, changelog_ts, op)`. One subtlety: StarRocks doesn't support row-tuple comparison, so the range predicate is decomposed by hand into `(synced_at > %s OR (synced_at = %s AND _changelog_row_id > %s))`, which matches the table's key prefix and stays a cheap range scan.


## 8. Cost optimization (~20% reduction)

**Q14: What in this architecture drives cross-region cost, and what are the real levers?**

The multi-region work is the direct source: three regional Debezium instances (EU/US/CN), each with its own Pub/Sub topic set, feeding one unified RisingWave/StarRocks cluster that does a `UNION ALL` of the three regional CDC tables inline, tagging every row with a region column that threads through every MV and model. Wherever that centralized cluster physically lives, every other region pays cross-region egress on every CDC message flowing into shared compute.

Two concrete levers: **GCS state-write frequency** — RisingWave's Hummock state store checkpoints streaming state to object storage on a barrier interval; every checkpoint is a write, and a cross-region write if the bucket isn't co-located with compute — tuning checkpoint cadence and bucket-region co-location cuts both write-op cost and cross-region egress, at the cost of slightly larger recovery-replay windows. **Background processing** — batched SQLMesh deploys with a sleep between batches to avoid a thundering-herd hitting the cluster (and egress) all at once, and readiness polling deliberately using a cheap existence probe instead of an expensive full scan. Same cost-conscious instinct applied to different axes (compute vs. network).

*Be ready to defend:* don't overstate precision — the architecture plausibly explains a ~20% story, but there's no cost-attribution report breaking out exactly which lever delivered what fraction. If asked for the exact breakdown, say you'd want the real billing data in hand.

## 9. StarRocks partition, distribution, and bucket design

**Q15: Walk me through what partition, distribution key, and bucket mean in StarRocks — use one of your real tables.**

Take `contexts.account`: `partition_by = 'region'`, `distributed_by = 'HASH(org)'`, `buckets = '64'`. Partition is the coarse, top-level split — a separate physical partition per distinct `region` value (`us`, `eu`, `cn`), maybe 3-5 total, since region is low-cardinality. It buys two things: query pruning (a query filtering `WHERE region = 'us'` never opens the `eu`/`cn` partitions at all) and cheap lifecycle management (`DROP PARTITION` is a metadata-only op, versus a row-by-row `DELETE` that then needs compaction to reclaim space — which is exactly why the changelog tables instead partition on `date_trunc('day', changelog_ts)`, so a nightly retention job can drop a whole day's partition in one shot).

Distribution/bucketing is the split *within* a partition. Each partition is further divided into a fixed number of buckets (physically, tablets — independent storage units, each living on some StarRocks BE node). The distribution key decides which bucket a row lands in via `hash(key) % bucket_count`. For `account`, every row in the `region='us'` partition gets hashed by its `org` value into one of 64 buckets, deterministically — same org always lands in the same bucket. That buys parallelism and load spread across BE nodes.

Net: total tablets = partitions × buckets-per-partition, and that number is what the compaction daemon actually has to service. A query like `WHERE org = 'abc123' AND region = 'us'` prunes twice — partition pruning skips straight to the `us` partition, then bucket pruning (since `org` is exactly the distribution key, matched by equality) reads only the one bucket `hash('abc123') % 64` lands in. So a query that looks like a table scan actually touches one tablet out of `3 regions × 64 buckets = 192`.

**Q16: You mentioned changing the partition/distribution keys because compaction jobs were running too much — what exactly changed?**

Real commit: `71996f7`, "MAI-1942 — Switch StarRocks tables from org partitioning to org hash distribution," touching every current-state table's model file. Before: `distributed_by = 'HASH(id)'`, `partition_by = 'org'`, no explicit `buckets` (auto-sized). After: `distributed_by = 'HASH(org)'`, `buckets = '64'`, `partition_by = 'region'`.

The mechanism: partitioning by `org` on a multi-tenant platform means potentially thousands of partitions — one per tenant. With no explicit bucket count, StarRocks auto-sizes buckets from the table's data volume *at CREATE TIME* — but these tables are always empty when SQLMesh creates them, since data only starts arriving afterward via the RisingWave sink. Auto-sizing had nothing real to size against, so it defaulted small — close to one bucket per org-partition. Result: thousands of tiny tablets, every one getting hit continuously by RisingWave's small streaming upserts, so the compaction daemon was running nonstop across all of them merging small delta files. The fix collapses partition cardinality from *(number of orgs)* down to *(number of regions)* — a handful of values — with a fixed 64 buckets pinned explicitly instead of trusting auto-sizing against an empty table. Same total data, a couple hundred bounded tablets instead of thousands that scale with tenant growth.

**Q17: Why move the distribution key from `HASH(id)` to `HASH(org)` specifically — isn't that a separate fix from the partition change?**

They had to ship together — it's the other half of the same fix, not an independent tweak. Under the old scheme, `org` was the partition key, so org-level query pruning was already happening for free at the partition level; within that, `HASH(id)` made sense because it spreads one org's rows evenly across buckets for write parallelism, with zero downside since pruning was already handled one level up. The moment `org` stopped being the partition key, that free pruning disappeared — and in this system, essentially every query is scoped `WHERE org = '<org>'` (single-tenant access pattern; the design doc states this explicitly for the changelog tables, which already used this pattern). Leaving the distribution key as `HASH(id)` post-migration would mean an org-scoped query has to fan out across all 64 buckets in a region partition, since `id`'s hash has no correlation with `org`. Switching to `HASH(org)` relocates the org-pruning responsibility from partition level to bucket level — an org's rows still land deterministically in the same handful of buckets, so the pruning property survives the migration.

One assumption to name if pressed: this only holds cleanly if orgs are reasonably balanced — a single very large tenant pins to a few hot buckets rather than spreading out. That's the exact opposite tradeoff the append-only changelog tables make: they hash on `(org, _changelog_row_id)` — not `org` alone — specifically because they're unbounded and append-only, so a high-volume org's ever-growing row count needs to spread across all buckets rather than pile into a few forever. Those tables also pin bucket count explicitly (16, lower than the current-state tables' 64) because for them buckets multiply by active day-partitions under a ~30-day retention window, so a higher fixed count would reintroduce the same tablet-bloat problem in a different shape.

**Q5 — the one to have completely nailed: Why didn't this become production? Walk me through the actual reasoning behind choosing RisingWave + StarRocks instead.**

I want to be careful here because it's easy to make this sound like "Iceberg is bad" — it isn't. It's about fit for *this specific* workload: continuous, low-latency CDC feeding a serving layer that needs to answer queries fast, not a lakehouse primarily feeding BI/analytics tools. Four things came out of the POC:

*First, small-writes metadata growth — real, but more precisely a catalog-tooling gap than a fundamental Iceberg limitation.* CDC is a stream of small, frequent, per-document mutations; each commit adds files/manifests/snapshots, and I proved this to myself by literally hitting the 429 metadata-too-large error. I want to be precise here rather than overclaim: Iceberg itself handles small writes fine as long as compaction runs behind them — the actual blocker was that BigLake's catalog-impl client didn't support the `CALL` procedures needed to run that compaction at all, which I found and fixed by switching to the native REST catalog client against the same endpoint (measured result: files down 81%, manifests down 94%). So this wasn't "Iceberg can't do CDC" — it was "the specific catalog client we were using couldn't maintain itself, and once maintenance actually worked, it kept up." What's still true and not just a tooling gap: even with maintenance working, that's an *additional* piece of production infrastructure — a scheduled job, its own monitoring — that a continuously-ingesting workload needs and a batch-ingested lakehouse mostly doesn't. RisingWave is a streaming database built around continuous ingestion as the first-class case; there's no analogous "you must run a separate maintenance job or your metadata grows unbounded" operational tax.

*Second, the raw CDC tables were append-only change logs, not current-state tables.* Every write was a plain append — no upsert, no primary-key merge on the base entity tables. Every consumer has to independently reconstruct current state by windowing/deduping, which is exactly the logic I had to hand-build in the one place I did implement upserts. If every downstream consumer has to reimplement dedup, you haven't built a serving layer, you've built a change log with extra steps. StarRocks' primary-key tables do merge-on-read upsert natively, at query time, without hand-rolled combine logic.

*Third, the upsert mechanism I did build wasn't atomic, and I knew it going in.* The upsert path was delete-matching-keys then append — two separate Iceberg commits. Between them there's a window where a concurrent reader sees a key duplicated or briefly absent. Tolerable for internal curated tables; not for anything customer-facing. Building genuinely atomic MERGE would have meant standardizing back onto Spark Structured Streaming (Spark's MERGE INTO is atomic; PyIceberg from Beam doesn't expose it), which puts me back into fighting Dataproc's TTL. RisingWave gives correct incremental upsert semantics as a language primitive, not something I bolt together out of delete-then-append.

*Fourth, operational surface area.* By the end I had two ingestion engines with duplicated transform logic, a REST catalog integration with its own credential-vending quirks, long-running-job token-refresh logic, a maintenance job that itself needed monitoring, and a soft-delete broadcast hack every downstream consumer needed to know about. None of that is exotic, but it's a lot of moving, GCP-specific parts for a data platform team to own, versus a two-component architecture where each piece does the one job it was purpose-built for.

The honest framing: Iceberg-on-GCS won on cost-at-rest and analytical engine-interoperability, but lost on write-latency fit, upsert correctness, and operational complexity for a real-time CDC-to-serving use case — and those were the dimensions that actually mattered here.

**Q6: More generally, when is the lakehouse pattern the right call versus a dedicated streaming OLAP layer?**

Three axes: write pattern, query pattern, engine interoperability. Iceberg wins when writes are batch/low-frequency-large, data needs to be queried by multiple heterogeneous engines (this POC's tables were queryable from BigQuery and equally could be from Trino/Flink/Spark without copying data), and cost-at-rest matters more than query latency. That's the profile of ML feature stores, historical analytics, compliance/audit data lakes. A dedicated engine like StarRocks wins when writes are continuous, query latency needs to be sub-second at real QPS, and you don't actually need five engines hitting the same bytes. The tell in this POC: I kept needing to build database-like behavior on top of Iceberg by hand — upsert semantics, current-state materialization, compaction scheduling. Every time I reimplemented a feature a purpose-built database gives for free was a signal I had the wrong tool for *this* job.

**Q7: How do you actually do upserts into an append-optimized format like Iceberg?**

Two standard patterns: copy-on-write (a matching row triggers a full rewrite of its data files) and merge-on-read (equality/positional delete files reconciled at read time, compacted later). Spark's native MERGE INTO supports both. I wasn't in a position to use it directly since the transform ran on Beam via PyIceberg, whose write API didn't expose atomic MERGE at the time — so I hand-built a poor-man's merge-on-read: split each micro-batch into deletes and upserts, build an equality-delete filter per key, delete matching rows, then append the new versions. Gets you upsert *behavior*, but as flagged above, two non-atomic commits — the honest caveat I'd volunteer before being asked. If I were doing it again on Iceberg, I'd push the transform back onto Spark for real atomic MERGE, at the cost of reintroducing the TTL problem.


**Q9: How did you handle MongoDB deletes — I noticed deletes get broadcast to every table?**

Good catch — a deliberate hack I'd rather own than have someone find. MongoDB's change-stream delete event doesn't include the deleted document by default, only its `_id` — no way to know which object type it was, so no way to know which target table should receive the soft-delete marker. Workaround: construct a synthetic delete record with the type field null and broadcast it to every target table. Functionally correct, nothing missed, but wasteful — every table but the right one receives a delete marker for a type it never had, and downstream consumers have to filter those out. The real fix is enabling pre/post-images on the Mongo collection so the delete event carries the deleted document's type directly — I didn't do that in the POC because turning it on has its own storage/oplog overhead I didn't want to force onto a database I didn't fully own yet. Honest "this was a shortcut" answer if asked.


**Q11: Is there a version of this you'd revisit Iceberg for?**

Yes — important to be able to say this, because the decision wasn't "Iceberg loses," it was "Iceberg loses for this workload." If the requirement had been durable, cheap, long-retention, engine-agnostic access to raw change history for data science and multiple analytical engines, Iceberg on GCS would be exactly right, and most of what I built here would carry over unchanged. It broke down specifically on the combination of continuous low-latency writes plus correct upsert semantics plus a serving-latency bar. In practice I'd consider a hybrid down the line: RisingWave/StarRocks for the hot serving path, with a periodic export of the same CDC stream into Iceberg as the cheap long-retention analytical archive.

# Part 3 — Trino federation over MongoDB (the phase before CDC)

Two generations: a Node.js implementation using the Trino Thrift Connector protocol, then a reimplementation as native Java Trino SPI connectors (Cortex for single-org, Study for cross-org studies with a write path). This is the "Replaced cursor-based reporting with Trino federating queries... then moved off federation" line on your resume.

**Q1: Trino ships a MongoDB connector out of the box — why build two generations of custom connectors instead?**

The stock connector gives a static 1:1 database→schema, collection→table mapping. Doesn't match our shape at all. Tenancy isn't separate databases — every document in a shared collection carries an `org` (and for cross-org Study queries, an `account`) field, and a "table" is really `{org, object}` filtered out of one big collection. Schema isn't fixed — it's dynamic per org/account/study, sourced from an external schema service, because clinical trial forms are customer-configurable and the column list differs per tenant without a code deploy. And row/column-level access control is enforced by OPA policy that has to become part of the MongoDB query itself, not applied after rows cross the network. None of that — dynamic external schema, org/account-scoped multi-tenancy baked into the catalog, policy-as-query-filter — is something a generic connector can do.



**Q7: What did "stopped scaling with study volume" concretely mean?**

A few concrete failure modes I actually saw: the cross-org connector calls the schema service once per org, synchronously, inside the split-building loop — for a study with hundreds of orgs, that's hundreds of sequential HTTP round trips just to plan the query, before reading a single row, and it scales linearly with study size. Each split is a full Mongo query against a shared multi-tenant collection also serving live application traffic — no independent scaling knob for analytics load versus OLTP load beyond adding general Mongo capacity. Row-to-columnar conversion runs inside the connector process per query — CPU/memory pressure that scales with concurrent query count, not something Mongo or Trino elastically absorbs. And structurally, the write-path table registry is a static in-memory map — registrations don't survive a coordinator restart and don't propagate across multiple coordinators, so you can't even horizontally scale the metadata layer at real scale. All of it pointed the same direction: federation added query-time work with every additional study instead of pre-computed, horizontally scalable state — exactly what CDC-into-a-warehouse solves by moving transform-and-materialize off the query hot path.
